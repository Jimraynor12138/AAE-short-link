# 01 · 需求分析与技术方案（第一阶段存档）

> 本文档为第一阶段（需求分析与技术方案设计）的产出存档，作为后续所有版本实施的设计依据。

## 1. 系统定位

高性能短链接系统，作为真实 Java 后端学习项目，实践：高并发、缓存、分布式 ID、消息队列、数据库设计、性能优化。同时作为使用 AI Coding Agent 完整开发软件的学习载体。

## 2. 业务流程

```
【创建链路】
用户提交长URL(可含过期时间、分组) → 发号器生成短码 → 落库(短码↔长URL映射) → 写缓存(V1起) → 返回短链

【跳转链路（核心高并发链路）】
浏览器访问短链 → 查缓存(未命中查DB回填) → 校验(存在/未过期/未停用) → 异步记录统计 → 302 重定向
```

核心认知：跳转链路读 QPS 通常远高于创建链路（10:1 甚至更高），设计重心在"短码→长URL"高频读。

## 3. 版本边界

| 版本 | 内容 | 明确不做 |
|---|---|---|
| V0 | 创建/302跳转/CRUD(逻辑删除)/分组/过期停用校验，DB 自增发号 | 缓存、统计、MQ |
| V1 | Redis 短码缓存(TTL抖动)、Redis INCR 发号、PV/UV 统计(HyperLogLog) | MQ、分库分表 |
| V2 | RabbitMQ 统计异步化(跳转发消息即返回)、统计查询接口 | 分库分表、微服务 |
| V3 | 防穿透(空值缓存+布隆过滤器)、防击穿(热点逻辑过期)、防雪崩(限流降级)、Caffeine 多级缓存、Snowflake/号段发号对比 | 分库分表 |
| V4(可选) | 千万级造数、冷热分离/归档、ShardingSphere 分库分表、读写分离 | — |

第一版不做：分库分表、微服务、多租户、OpenAPI、CDN 边缘跳转。

## 4. 数据库设计

见 `02-数据库设计.md`。要点：
- `t_link`：跳转链路唯一依赖表，`(domain, code)` 唯一索引，逻辑删除
- `t_link_stats`：按 link_id + 日期聚合，写入量从"每次点击"降为"批量聚合"
- `t_sequence`：V0 发号表，V1 起由 Redis 替代
- `t_group` / `t_user`：分组管理 / 极简登录（单管理员）

## 5. 发号方案决策

短码 = 发号器产出的 long ID + Base62 编码（6 位容量约 568 亿）。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| DB 自增 | 极简、绝对有序 | 高并发锁竞争、强依赖 DB、可被按序遍历 | V0 使用 |
| Redis INCR | 原子、高性能、简单 | Redis 强依赖、持久化丢号风险 | V1 使用 |
| 号段模式 | DB 压力降为 1/N、双 buffer 预取 | 短码偏长、多一套号段管理 | V3 实现 |
| Snowflake | 本地生成、不依赖存储 | 时钟回拨、机器 ID 分配 | V3 实现（含回拨处理） |

生产典型选择：号段模式(Leaf-segment 类)或 Snowflake 变体；BAT 级短链多见预生成号池。

## 6. Redis 使用场景

1. 短码映射缓存（核心）：`short-link:link:{domain}:{code}` → URL/状态，命中不碰 DB
2. 发号器：INCR
3. UV 去重：HyperLogLog（约 12KB/key，而非 Set）
4. 布隆过滤器（V3）：拦截随机猜码扫描
5. 空值缓存（V3）：防穿透

定位原则：缓存是性能加速层而非数据源，可全量丢失后从 DB 重建。

## 7. 缓存三大问题对策（按版本演进）

| 问题 | 对策 | 引入版本 |
|---|---|---|
| 穿透（不存在的短码打 DB） | 空值缓存(短TTL) + 布隆过滤器 + 限流 | V1 空值 / V3 布隆 |
| 击穿（热点码过期瞬间打 DB） | 逻辑过期/不过期+异步刷新、互斥锁重建 | V3 |
| 雪崩（key 集体过期/Redis 宕机） | TTL 随机抖动、高可用、熔断限流降级 | V1 抖动 / V3 降级 |

## 8. RabbitMQ 取舍

- V1 不引入：低访问量下同步 update 或内存聚合+定时落库足够
- V2 引入，只服务明确场景：① 统计异步化（跳转 RT 与统计写库解耦）② 削峰填谷 ③ 未来解耦订阅（过期通知等）

## 9. 性能瓶颈认知（跳转链路）

DNS/网络 RTT → 应用线程模型（禁止跳转路径同步慢调用）→ 缓存未命中 DB 查询 → 热点 key（单 key 打满分片，需本地缓存/key 打散）→ 统计同步写 → 连接池配置。

学习方法论：压测驱动优化——每版本用 JMeter/wrk 采集 QPS/RT/命中率留档，用数据验证升级决策。

## 10. 数据量演进认知

- 千万级：单表尚可扛，但备份/DDL/慢查询/缓存命中率问题显现，统计表先到瓶颈
- 亿级：索引变高、单机存储与写入上限、主从延迟、DDL 不可行（需 gh-ost 类工具）
- 关键洞察：短链访问呈强二八/长尾分布，读靠缓存热数据消化，写增长线性；先做冷热分离/归档，分库分表是最后手段（ShardingSphere 按 id 哈希，保证跳转单分片命中）

## 11. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | JDK 17 + Spring Boot 3.2 | 主流 LTS 组合 |
| Web | Spring MVC | 跳转是简单请求，不引入 WebFlux 复杂度 |
| ORM | MyBatis-Plus | CRUD 高效、SQL 可控，便于学习索引优化 |
| DB | MySQL 8 | 核心存储 |
| 缓存 | Redis(Spring Data Redis + Redisson，V1 起) | 映射缓存/发号/HLL/布隆 |
| MQ | RabbitMQ（V2 起） | 部署轻、控制台友好、消息模型教学价值高 |
| 本地缓存 | Caffeine（V3 起） | 热点 key 二级缓存 |
| 分片 | ShardingSphere-JDBC（V4 可选） | Java 生态事实标准 |
| 压测 | JMeter / wrk | 版本演进量化工具 |
| 辅助 | Maven / Lombok / Hutool / Knife4j | 减少样板代码 |

明确不引入（当前阶段）：微服务框架、K8s、Elasticsearch、Kafka。

## 12. 学习项目 vs 生产系统

| 维度 | 学习项目 | 生产系统 |
|---|---|---|
| 发号 | 全部方案亲手实现 | 号段/Snowflake 为主 |
| MQ | 出现真实瓶颈才引入 | 中大型普遍上（多为 Kafka 类管道） |
| 分库分表 | 造数据也要练一遍 | 绝大多数到不了亿级，先冷热分离 |
| 高可用 | 单机即可 | 哨兵/集群、多机房、降级预案 |
| 关注点 | 理解"为什么" | 可运维、可监控、可回滚 |
