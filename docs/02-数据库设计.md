# 02 · 数据库设计

> 建表脚本：src/main/resources/sql/schema.sql（MySQL 8）

## ER 关系

```
t_group (gid)  1..N  t_link (gid)      一个分组包含多个短链
t_link  (id)   1..N  t_link_stats      一条短链对应多日聚合统计
t_user               分组/短链的所有者（V1 极简登录接入）
t_sequence           独立发号表，与业务表无外键关联
```

设计原则：跳转链路只依赖 t_link 单表；统计写入全部隔离到 t_link_stats；表级别实现读写分离。

## t_link 短链接表（核心）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 发号器产生的号（IdType.INPUT），code = Base62(id) |
| code | varchar(16) **COLLATE utf8mb4_bin** | 短码，**必须区分大小写**（见下方说明） |
| domain | varchar(128) | 短链域名 |
| original_url | varchar(768) | 原始长 URL（768 避免索引超长限制） |
| gid | varchar(32) | 分组标识，默认 default |
| enable_status | tinyint | 0 启用 / 1 停用 |
| valid_type / valid_date | tinyint / datetime | 1 永久 / 2 自定义过期时间 |
| description | varchar(512) | 描述 |
| del_flag | tinyint | 逻辑删除（便于追溯，物理不删） |
| create_time / update_time | datetime | DB 默认值维护 |

索引设计：

- PRIMARY KEY (id)
- UNIQUE uk_domain_code (domain, code)：短码唯一性按域名隔离，跳转查询唯一入口
- idx_gid_create (gid, del_flag, create_time)：分组分页查询

### 为什么 code 必须用 utf8mb4_bin（区分大小写）

Base62 字符集**同时包含 `a-z` 与 `A-Z`**（共 62 个字符）。若沿用 MySQL 默认的
`utf8mb4_general_ci`（大小写不敏感），会同时踩两个坑：

1. **唯一索引失效一半**：`"2A"` 被判为与已存在的 `"2a"` 重复 → 新短码插不进去，id 空间被大量浪费
2. **跳转语义被破坏**：`WHERE code = '2A'` 会命中 `2a` 的记录 → `/2A` 与 `/2a` 指向同一条短链

本项目在 V3.5 的高并发 E2E 中实测到这两个现象（30 并发出现 23~26 次重复键错误，
被创建链路的「冲突→重试」兜底掩盖成"偶发冲突"）。修复即给该列显式声明
`COLLATE utf8mb4_bin`，实测冲突降为 0，且 `3c`(id 198) 与 `3C`(id 224) 可共存。

> 通用教训：**混合大小写的编码（Base62/Base64）落到关系库时，排序规则是数据模型的一部分**，
> 不能依赖数据库默认值。

## t_link_stats 访问统计聚合表

按 link_id + date 聚合（uk_link_date 唯一），把写入量从"每次点击一行"降为"每链每日一行"：

- pv / uv / ip_cnt：点击量、独立访客、独立 IP
- default_cnt：直接访问（无 Referer）
- referer_stats / device_stats / locale_stats：来源/设备/地域分布，JSON 文本存储（V2 消费端聚合写入）

索引：uk_link_date (link_id, date)、idx_code_date (code, date)（按短码查趋势）。

其中 `code` 同样使用 **`COLLATE utf8mb4_bin`**：与 `t_link.code` 保持一致，
否则按短码查统计时 `2A` 会与 `2a` 混在一起（详见 t_link 一节的说明）。

## t_sequence 发号序列表（V0）

单列自增表，INSERT 占位行 + RETURN_GENERATED_KEYS 取号。已知局限：表持续增长、高并发下自增锁竞争——这正是 V1 切换 Redis INCR 的动机，切换后保留作兜底。

## t_segment 号段分配表（V3.5）

一行一个业务：`max_id` 是「已分配到的最大号」，一次发号 = 一次
`UPDATE t_segment SET max_id = max_id + step WHERE biz_tag = ?`（靠主键行锁保证原子），
同事务内 `SELECT max_id` 读回上界。

- biz_tag：业务标识（主键），本项目固定 `short-link`
- max_id：已分配到的最大号；应用启动时会抬升到「不小于 `MAX(t_link.id)`」，避免跨发号器切换时重号
- step：号段长度（默认 1000）。越大 → 发号的 DB 压力越小，但重启浪费的号越多

与 `t_sequence` 的对比：发号的 DB 调用降为 **1/step**，且表不再增长（永远一行）。
代价是号有「段间跳变」（全局唯一、趋势递增，但不严格连续）。

实测（`docs/benchmark/V3.5-发号器对比.md`）：一次号段分配约 7ms，
`step=1000` 时每号摊销 **7µs**，而 Redis INCR 每号 **158µs**、DB 自增每号 **1393µs**。

## t_group 分组表 / t_user 用户表

- t_group：gid 随机生成（业务唯一键），name、sort_order，逻辑删除
- t_user：username 唯一、password 存 BCrypt 摘要（不存明文），V0/V1 仅单管理员

## 不使用外键的原因

互联网场景普遍不建物理外键：高并发下外键检查带来锁开销、影响插入吞吐，且分库分表后跨库外键无法存在。一致性由应用层保证。

## 未来演进预留

- 分库分表（V4）：按 id 哈希路由（ShardingSphere-JDBC），code 可由 id 推导故仍能单分片命中
- 冷热分离：del_flag=1 或长期零访问的链接归档到冷表
- 统计明细若需保留原始访问记录，走日志管道或明细宽表而非本表
