## 2026-10-02 · V1.1 Redis 缓存跳转优化

### 做了什么
- pom.xml：新增 spring-boot-starter-data-redis（不引 Redisson，V3 布隆过滤器时再说）
- 配置：Redis 连接（localhost:6379 无密码）+ shortlink.cache.*（ttl=1800s / jitter=600s / null-ttl=60s）
- 新增 cache/CacheKeyBuilder：key 构建 short-link:link:{domain}:{code} + TTL 抖动计算
- 新增 dto/LinkCacheDTO：缓存值（4 字段最小快照，约 200 字节）
- 新增 service/RedirectService + RedirectServiceImpl：跳转逻辑从 LinkServiceImpl 拆出
  - Cache Aside：查 Redis，未命中查 DB，回填（TTL 抖动）
  - 空值缓存：不存在写 "null" 标记，TTL 60s 防穿透
  - 降级：Redis 读/写异常均捕获，降级直查 DB，跳转可用性优先
  - 缓存值损坏（非法 JSON）：warn 日志 + 回源，不直接失败
- 修改 LinkServiceImpl：updateLink/deleteLink 末尾删除缓存（先改库后删缓存，删失败仅记日志）
- 修改 RedirectController：改注入 RedirectService
- 测试：RedirectServiceImplTest 12 个用例；UpdateTest 补缓存删除断言；原跳转测试类迁移删除

### 关键决策
1. 缓存数据快照，不缓存"可跳转"结论——否则"缓存时未过期、后来过期"的短链会继续放行
2. 创建不写缓存（懒加载）——创建量可能远大于访问量，首次访问自动回填
3. 先改库后删缓存——删失败时脏数据最多活到 TTL，TTL 是最终一致性兜底
4. TTL 抖动 1800+[0,600]s——防大量 key 同时到期（雪崩第一层防护）
5. 缓存停用/过期短链的快照——下次命中后应用侧判定，减少对已停用短链的 DB 回源

### 学习点
- Cache Aside 模式：读时回填、写时删除；为何不是"写时更新缓存"（并发写乱序会旧值覆盖）
- 空值缓存与 TTL 的权衡：太长会挡住"刚创建的短码"（60s 折中）
- Mockito：void 方法打桩用 doThrow().when()；MP updateById(any()) 有 Collection 重载歧义需显式类型

### 踩坑
- ValueOperations.set(key, value, Duration) 返回 void，when() 打桩编译报"空类型不允许"
- Mockito 严格模式下 setUp 打桩若某用例未用到抛 UnnecessaryStubbing，需 lenient()
- Windows cmd 的 timeout 不支持重定向环境，等待用 ping -n N 127.0.0.1 代替

### 验证结果
- 单元测试 39/39 通过
- 端到端验证（应用实跑 + curl + redis-cli）：
  - 创建短链到 302 + Location 正确
  - 首次跳转回填缓存，TTL=2053s（1800+[0,600] 抖动区间内）
  - 不存在短码到 404 + 空值缓存（值 "null"，TTL 60s）
  - 修改短链 URL 到 缓存 EXISTS=0（已删）到 再跳转回源指向新 URL 并回填新值

## 2026-10-02 · V1.2 Redis INCR 发号器

### 做了什么
- 新增 `idgenerator/RedisIncrIdGenerator`（`@ConditionalOnProperty` 按 `shortlink.id-generator-type=redis` 装配）
  - 启动播种：`SETNX short-link:id-generator <DB 当前最大 t_link.id>`
  - 发号：`INCR`（单次原子操作，替代 V0 的 t_sequence INSERT）
  - **丢号自愈**：若 INCR 返回 1（说明 key 曾被清空/Redis 重启），按 DB 最大值重新播种并跳过安全区间
- `LinkServiceImpl.createLink`：增加短码冲突重试（最多 3 次），捕获 `DuplicateKeyException` 后重新发号
- 测试：`RedisIncrIdGeneratorTest` 5 例；`LinkServiceImplCreateTest` 增 2 例重试用例

### 关键决策
1. 为什么还要保留 DB 唯一索引兜底：Redis 是内存存储，重启/主从切换/FLUSHALL 都可能丢计数 → 重号，唯一索引是最后一道防线，配合应用层重试即可自愈
2. 播种基准用 `t_link` 的 MAX(id) 而非 t_sequence：t_link.id 才是真正用过的号，其之上的号可安全复用（V0 浪费的号不占用）
3. 发号器保留可插拔：V0 的 `AutoIncrementIdGenerator` 仍在，改配置即可回退对比（有利于压测对照）

### 学习点
- Redis 发号 vs DB 自增：把创建链路的 DB 写从 2 次降到 1 次，DB 从「发号 + 落库」变为只负责落库
- 发号器「不可靠存储」的通用处理套路：播种 + 越界检测 + 唯一键兜底 + 重试
- `INCR` 返回 1 的意义：正常情况这是首个号；但配合播种策略，它也成了「key 丢失」的探测信号

### 验证结果
- 单元测试：53/53 通过
- 端到端（`--shortlink.id-generator-type=redis` 实跑）：
  - 启动播种值 = 2（DB 当前最大 id，正确）
  - **并发 20 次创建 → 20 个唯一短码**（3,4,...,m 连续，无重号）
  - DB 校验：22 条记录 / 22 个唯一 code，无冲突

## 2026-10-02 · V1.3 访问统计（PV/UV/IP，HyperLogLog）

### 做了什么
- `CacheKeyBuilder`：新增 PV / UV / IP 三类统计 key（按 `日期 + 短码` 维度）
- `ShortLinkProperties`：新增 `stats-ttl-seconds`（默认 7 天）
- 新增 `dto/StatsRespDTO`、`service/StatsService` + `impl/StatsServiceImpl`、`controller/StatsController`
  - PV：`INCR short-link:stats:pv:{date}:{code}`
  - UV：`PFADD short-link:stats:uv:{date}:{code} <md5(ip|ua)>`（同 IP 换设备算两个访客）
  - 独立 IP：`PFADD short-link:stats:ip:{date}:{code} <ip>`
  - 首次写入时顺手 `EXPIRE` 三个 key（省一次 RTT）
- `RedirectService` 签名扩展为 `(code, clientIp, userAgent)`；`RedirectController` 提取 IP/UA（优先 X-Forwarded-For，为 V3 前置 Nginx 预留）
- 统计只在跳转成功时记录；统计异常全部吞掉（旁路能力不影响主链路）
- 测试：`StatsServiceImplTest` 5 例；`RedirectServiceImplTest` 增「成功记录统计 / 校验失败不统计」2 例

### 关键决策
1. **UV/IP 用 HyperLogLog 而非 Set**：HLL 固定约 12KB/key 且可估算海量基数（误差约 0.81%）；改用 Set 存原始访客，一个热点短码一天就能吃掉大量内存
2. **UV 身份 = md5(ip + UA)**：单用 IP 会把「同一办公网出口（NAT）下的多个用户」算成 1 个；加上 UA 更接近真实访客
3. **统计是旁路**：所有异常捕获，统计失败绝不阻塞跳转
4. V1 同步统计（跳转链路上 +3 次 Redis RTT）——这是**有意保留的痛点**，V2 用 MQ 异步化，正好形成可对比的优化案例

### 学习点
- HyperLogLog 在 UV 统计中的工业用法（基数估算换内存）
- 旁路能力的异常隔离设计：主链路可用性 > 统计数据完整性
- 统计维度设计：同日同码维度、按天 key 天然分片、TTL 即数据保留窗口

### 验证结果
- 单元测试：53/53 通过（含新增 7 例）
- 端到端实测：
  - 同一 UA 连续 3 次跳转 + 换 UA 跳转 1 次 → 统计接口返回 **PV=4、UV=2、IP数=1**（与预期完全一致）
  - Redis 中存在 3 个 key：`stats:pv/uv/ip:2026-10-02:3`

### 结果（QPS / avg / p95 / p99）
| 场景 | QPS | avg | p95 | p99 | max |
|---|---|---|---|---|---|
| S1 V0 等价 | 3443 | 25.0ms | 86ms | 187ms | 637ms |
| S2 仅缓存 | **5369** | **15.7ms** | **30ms** | **47ms** | **121ms** |
| S3 V1 现状 | 3439 | 26.6ms | 47ms | 60ms | 74ms |
| S4 仅统计 | 2489 | 37.5ms | 58ms | 97ms | 354ms |

### 关键结论
1. **缓存收益显著**：QPS +56%，p95 -65%，p99 -75%——长尾改善（消除 DB 连接池排队）远大于均值改善
2. **同步统计代价巨大**：加统计后 QPS 掉 28%~36%，avg 涨 50%~69%。**V1 现状的吞吐几乎回落到 V0 基线**——缓存赚的，被统计抵消了
3. **这就是 V2 引入 MQ 的量化依据**：V2 验收标准 = S3 场景 QPS 回到接近 S2（5000+）、avg 回到 15ms 量级
4. 意外观察：S3 的 p99 反而优于 S1——统计开销是均匀的，DB 排队是有偏的

### 踩坑（压测方法论）
- **JMeter 默认向已有 JTL 追加样本**：第二次跑 S1 时混入上次 1 万条样本，时间跨度算成 1873s，QPS 变 10.7（严重失真）。解决：`jmeter -f` + 运行前删旧文件
- **预热不足数据完全失真**：同一场景预热 200 请求时 avg=16.38ms，预热 2000 请求后 avg=3.19ms（低并发）
- **ramp-up 会稀释 QPS**：5s 爬坡 + 短测试（5s）时，QPS 被算成 1900；改 ramp=1s 后才是稳态值 3443
- Windows 执行策略默认禁止脚本，需 `-ExecutionPolicy Bypass`

## 2026-10-02 · V2 统计异步化（RabbitMQ）

### 决策（执行前与用户确认的 4 点）
1. 统计**可容忍偶发丢失**：fire-and-forget，投递失败只记日志，绝不影响跳转（不引入 publisher confirm + 本地消息表）
2. 统计存储：**Redis 为实时口径 + 定时快照落 MySQL `t_link_stats`**
3. 维度扩展：**来源（Referer）+ 设备（UA）**，地域留到后续版本
4. 消费失败：**重试 3 次 + 死信队列**，不做无限重投

### 做了什么
- **依赖/配置**：`spring-boot-starter-amqp`；`shortlink.mq.*`（交换机/队列/路由键/DLX/幂等 TTL）、`shortlink.stats-persist.*`（落库间隔、批次）
- **MQ 拓扑**（`mq/config/RabbitMqConfig`）：DirectExchange `short-link.visit.exchange` → 队列 `short-link.visit.queue`（durable，绑定 DLX）→ 死信交换机/队列；消息体用 JSON 转换器（管理台可直接看内容）
- **生产者**（`mq/producer/VisitMessageProducer`）：构造消息（UUID 作为幂等 ID）+ 投递；异常全吞
- **消费者**（`mq/consumer/VisitStatsConsumer`）：幂等校验 → 写 Redis 实时统计 → 标记脏短码；失败释放幂等标记并抛异常（触发重试→死信）
- **幂等**（`mq/IdempotentChecker`）：`SETNX short-link:mq:consumed:{visitId}`，TTL 600s；Redis 异常时按"首次消费"处理（宁可重复不可丢）
- **快照落库**（`service/impl/StatsSnapshotServiceImpl`）：内存脏标记 + `@Scheduled` 每 2 秒批量 upsert；`@PreDestroy` 停机前兜底 flush；用 `INSERT ... ON DUPLICATE KEY UPDATE` 做幂等快照覆盖
- **跳转链路改造**：新增 `VisitRecorder` 门面，按 `shortlink.mq.enabled` 装配 `AsyncVisitRecorder`（投递 MQ）或 `SyncVisitRecorder`（V1 同步行为，降级路径）；`RedirectService` 签名增加 `referer` 参数
- **解析工具**：`UserAgentParser`（mobile/tablet/bot/pc/unknown）、`RefererParser`（提取来源域名，无 Referer 记 `direct`）
- **统计维度**：新增 Redis Hash key `stats:referer:{date}:{code}`、`stats:device:{date}:{code}`（HINCRBY），查询接口返回 `refererStats`/`deviceStats`
- **测试**：新增 6 个测试类（UA 解析、Referer 解析、幂等、生产者、消费者、快照落库）并更新统计/跳转测试 → **81/81 通过**

### 关键设计决策
1. **Redis 是实时口径，MySQL 只是快照**：所以落库是"覆盖写"而不是"累加写" —— 天然幂等，重试也不会多加，避免了「消费端累加 + 重试 = 数据翻倍」的经典坑
2. **解析放在消费端**：UA/Referer 解析是 CPU 操作，放消费端可水平扩容；跳转线程只做一件事——投递
3. **幂等标记要在失败时释放**：否则重试会被自己的幂等标记挡掉（这是幂等 + 重试组合时最容易踩的坑）
4. **死信队列而非无限重试**：`default-requeue-rejected=false` + `max-attempts=3`，重试用尽进 DLQ
5. **保留同步降级路径**：MQ 挂了系统仍能统计（降级为 V1 行为），跳转可用性优先

### 踩坑
- **`@Scheduled(fixedDelayString)` 不支持 `2s`**：写 `"2s"` 直接启动失败（`Invalid fixedDelayString value "2s" - cannot parse into long`），它只认毫秒数字符串；写成 `"2"` 又会被当 2 毫秒疯狂写库 → 最终用 `flush-interval-ms: 2000`
- **Spring AMQP 消息转换失败**：非法 JSON 消息在进入监听方法**之前**就抛异常（MessageConversionException），同样会被重试并最终进 DLQ（已实测验证）
- **PowerShell 与 cmd 混用**：`&` 链式命令在 PowerShell 下报错；curl 的 JSON `-d` 在 PowerShell 里引号会被吞，需用 `--data-binary @文件`
- **JMeter 结果文件默认追加**（V1 已记录，本次沿用 `-f`）

### 验证结果（端到端实跑）
- 单元测试 81/81 通过
- RabbitMQ 拓扑自动声明：主队列 durable + DLX 参数、死信队列、消费者已连接
- 4 次跳转（带 Referer/UA 差异）→ 统计接口返回 `pv/uv/ipCnt` + `refererStats{direct:2, www.baidu.com:6}` + `deviceStats{mobile:6, pc:2}`，与请求完全对应
- MySQL `t_link_stats` 在 2 秒内写入快照，与 Redis 口径一致
- 死信队列实测：投递非法消息 → 重试 → 进入 `short-link.visit.dlq`（messages=1）
- 降级实测：`--shortlink.mq.enabled=false` 启动即回退同步统计，跳转正常

### 压测结果（详见 `docs/benchmark/V2-压测报告.md`）
| 场景 | 线程 | QPS | avg | p99 |
|---|---|---|---|---|
| S3 V1 同步统计 | 100 | 2873 | 32.3ms | 66ms |
| **S5 V2 MQ 异步** | 100 | **3672（+28%）** | **24.3ms（-25%）** | 75ms |
| S3 V1 同步统计 | 200 | 2753 | 68.9ms | 132ms |
| S5 V2 MQ 异步 | 200 | 3076 | 58.5ms | 250ms |

**未达成 5000+ 的验收目标**，原因已定位：S3 从 100 线程加到 200 线程吞吐不增、延迟翻倍 = 环境饱和（客户端+Broker+消费端+DB 同机争抢 CPU），不是架构问题。压测后队列积压 16483 条而跳转不受影响，正面验证了削峰填谷。

| 严重程度 | 问题 | 根因 |
|---|---|---|
| 🔴 高 | 消费端的「重试 3 次 + 死信队列」实际是哑弹 | `StatsServiceImpl.recordVisit` 吞掉所有异常，消费者只能捕获 `markDirty`（内存操作）的异常 → Redis 写统计失败时消息被正常 ack，重试/DLQ 都不会触发 |
| 🟠 中 | 幂等 key 数量 = QPS × TTL，600s 下约 180 万个 key | TTL 取值过于保守 |
| 🟠 中 | 跨零点丢统计 | 脏标记只存 code，flush 用「当前日期」反查 Redis，前一天的脏数据被当成「今天没数据」丢弃 |
| 🟠 中 | 重启丢脏标记 → 统计不再落库 | 脏标记是纯内存态，消息已 ack、Redis 有数据，但没有触发者 |
| 🟠 中 | visitId 为空的消息互相顶掉 | `tryConsume(null)` 固定 key，第一条之后全被误判为重复 |
| 🟠 中 | 重试可能重复累加 PV | 先写统计后标记脏，标记失败触发重试时会多加一次 |
| 🟡 低 | `VALUES(col)` 语法在 MySQL 8.0.20+ 已废弃 | 应改用行别名 |
| 🟡 低 | link_id 逐条查询 | 应批量 IN |

### 修复内容
1. **严格写入分离**：`StatsService` 新增 `recordVisitStrict(...)`（抛异常）；跳转线程继续用吞异常的 `recordVisit`，**消费端改用严格版**，让失败真正触发重试 → 死信队列
2. **幂等 TTL 600 → 60 秒**，并在配置注释里写明容量公式（key 数 ≈ QPS × TTL）
3. **脏标记携带日期**：引入 `DirtyKey(code, date)` 记录类；统计日期取自**消息时间**（`visitTime`），跨零点仍归入访问当天
4. **兜底扫描 `rescan()`**：用 SCAN 游标（非 KEYS）扫描当日 pv key，把有数据的短码重新标记为脏；启动时执行一次 + 默认每 10 分钟一次（可配 `rescan-interval-ms`，<=0 关闭）
5. **visitId 为空**：跳过幂等校验并告警，不再共用 `...:null` 固定 key；`release` 同样跳过空值
6. **执行顺序调整**：消费者先 `markDirty` 再 `recordVisitStrict`，消除重试重复累加 PV 的窗口
7. **upsert 改行别名**：`INSERT ... AS new ON DUPLICATE KEY UPDATE pv = new.pv`（MySQL 8.0.19+）
8. **批量解析 link_id**：一次 `IN` 查询替代逐条查询

## 2026-10-03 · V3.1 防穿透（布隆过滤器）

### 做了什么
- `bloom/BloomFilterHash`：双重哈希（MD5 派生 h1/h2 → `offset_i = (h1 + i*h2) mod m`）+ 参数公式（m、k 由容量与误判率推导）
- `bloom/ShortLinkBloomFilter`：基于 Redis BitMap（`SETBIT`/`GETBIT`）手写实现
  - **预热**：启动时从 DB 分批读取全部短码写入位图，完成后写 `init` 标记
  - **fail-open**：过滤器不可用（未初始化/Redis 异常）时一律放行，绝不误拦正常短链
  - **按需自愈**：位图丢失时，下一个请求会自动触发重新预热
- 配置：`shortlink.bloom.*`（enabled / capacity / false-positive-rate / key / init-flag-key / warmup-batch-size）
- 接入：`RedirectServiceImpl` 在**查缓存之前**做前置拦截；`LinkServiceImpl.createLink` 落库后同步写入位图（否则新短码会被自己误拦）
- 测试：`BloomFilterHashTest`（含**用内存 BitSet 实测误判率**）、`ShortLinkBloomFilterTest`，共新增 12 个用例

### 设计要点（布隆过滤器的三个坑）
1. **绝不能用 fail-close**：过滤器不可用时必须放行。若做成"不可用就拦截"，Redis 一抖动整站 404
2. **位图是外部状态，必须能自愈**：`init` 标记 + 位图 key **两者都要校验**（见下方 bug 2）
3. **不支持删除**：被删除的短码会永久留在位图中（判为"可能存在"），跳转时仍会走缓存/DB 并正确返回 404，只是少一次提前拦截

### E2E 过程中发现并修复的两个真实缺陷
**缺陷 1：两侧发号器共享同一 id 空间却没有对齐（V1.2 遗留）**
- 现象：`POST /api/v1/link/create` 连续报"短码生成冲突"
- 定位：`application.yml` 默认 `id-generator-type: auto`（DB 自增），而 `t_sequence` 的计数停在 ~7，`t_link` 的 id 已用到 22 → 切回 DB 自增后新号全是已用过的号（日志里的约束是 `t_link.PRIMARY`，id=8）
- 修复：`AutoIncrementIdGenerator` 启动时 `ALTER TABLE t_sequence AUTO_INCREMENT = max(t_link.id)+1`（只能抬高、天然单调），并实现 `recoverAfterConflict()` 二次自愈
- 同时给 `RedisIncrIdGenerator` 加了**单调抬升**（`INCRBY` 而非 `SET`，避免把计数改小）：启动抬升 + 冲突时抬升

**缺陷 2：布隆过滤器的 fail-close 陷阱（本次新引入，被 E2E 抓出）**
- 现象：手工删除位图 key 但保留 `init` 标记后，**真实短码 `/3` 返回 404**
- 根因：`initialize()` 只看 `init` 标记就认为"已就绪"，跳过了预热；位图不存在时所有位读出来都是 0 → 判定所有短码"一定不存在"
- 现实中的触发方式：Redis 的 `maxmemory` 淘汰策略可能丢掉大的位图 key 而保留小的标记 key
- 修复：`isReadyInRedis()` **同时校验标记与位图 key**，任一缺失就重新预热；补了对应单测
- 教训：**单元测试打桩了 Redis 状态，测不出这类"外部状态不一致"的问题**——必须靠 E2E 构造真实故障

### 验证结果
- 单元测试 **92 → 112 全绿**
- E2E：
  - 预热日志 `capacity=1000000, bitSize=9585059, hashCount=7, loaded=23`（与公式一致）
  - 位图字节数 1,185,106（约 1.13MB，对应 958 万位）
  - 已存在短码 `/3` → 302；随机短码 `/QQzz77` → 404
  - 新建短码 `n`（id=23）→ 立即可跳转 302（证明创建时写入位图生效）
  - **位图丢失自愈**：删除位图后重启 → 日志 WARN"位图丢失，重新预热" → `/3` 恢复 302

## 2026-10-04 · V3.2 缓存击穿防护（逻辑过期 + 互斥重建）

### 做了什么
- 缓存值 `LinkCacheDTO` 新增 `logicalExpireAt`（逻辑过期时间，epoch 毫秒）
  - 命中但已逻辑过期 → **立刻返回旧值 + 触发后台异步重建**，请求线程零阻塞
  - 兼容存量缓存：该字段为 null 一律视为"未逻辑过期"（否则升级瞬间会触发全量刷新，人为制造一次小雪崩）
- 新增 `cache/CacheRebuildLock`：Redis `SETNX` 重建锁（TTL 5s，互斥重建与异步刷新共用）；**fail-open**（Redis 异常视为已抢到锁）
- 新增 `service/CacheRefreshService(+Impl)`：异步重建的三道闸门
  1. 本机去重（`ConcurrentHashMap.newKeySet`）防止同一 key 重复入队
  2. 分布式重建锁（多实例之间只放一个回源）
  3. 有界队列 + `DiscardPolicy`（队列满直接丢弃：刷新是尽力而为，请求已拿到旧值）
- 新增 `config/CacheExecutorConfig`：刷新线程池（默认 2 线程、1000 有界队列、线程名 `cache-refresh-`）
- 新增 `cache/LinkCacheAssembler`：回填与异步刷新共用同一份缓存值装配，避免两处逻辑漂移
- `RedirectServiceImpl` 读路径改造：
  - 命中 + 逻辑过期 → 返回旧值 + 触发刷新（try/catch 兜底：刷新异常绝不影响跳转）
  - 未命中 → **互斥重建**：抢到锁者（leader）回源并回填；未抢到者（follower）按 `mutex-wait-millis` 轮询等待
  - follower 等待超时 → 自行回源但**不回填**（避免写放大），并记 WARN 便于排障
  - 补「未抢到锁 / 跟车成功 / 等待超时」的 DEBUG/WARN 日志
- 配置项 `shortlink.cache.anti-breakdown.*`：`logical-expire-enabled`(true) / `logical-expire-seconds`(300) / `mutex-rebuild-enabled`(true) / `mutex-wait-millis`(200) / `mutex-wait-step-millis`(20) / `refresh-pool-size`(2) / `refresh-queue-capacity`(1000)
- 测试：新增 `CacheRebuildLockTest` 5 例、`CacheRefreshServiceImplTest` 6 例，`RedirectServiceImplTest` 增 8 例

### 关键决策
1. **跳转场景以「逻辑过期」为主策略，而非「互斥锁等待」**：短链 URL 基本不变，"稍旧"几乎无害，却能换来请求线程零阻塞。让用户等锁在跳转场景是不必要的代价——互斥重建只作为"缓存真空"时的兜底
2. **物理 TTL 与逻辑过期时间分离**（1800s+抖动 vs 300s）：逻辑过期后 key 仍在，异步刷新窗口长达二十多分钟；即便刷新失败也不至于触发回源雪崩
3. **异常边界必须贴住故障点**：`catch (Exception)` 只包住 Redis `get`。第一版把"刷新触发 + 跳转校验"也包进去，导致刷新异常被误判成"Redis 故障"并多查一次 DB（被单元测试抓出）
4. **刷新能力双重兜底**：实现内部吞异常 + 调用方 try/catch（旁路能力绝不能拖倒主链路），与既有 `StatsService` / `VisitMessageProducer` 的口径一致

### 学习点
- 缓存击穿的两种工业解法与取舍：**互斥重建**（强一致、部分请求要等）vs **逻辑过期**（弱一致、绝对不阻塞）；读多写少且可容忍短暂陈旧的场景，后者更优
- **"锁窗口 = 回源耗时"**：互斥重建的收益完全取决于锁持有时间，回源越快收益越小
- 旁路任务必须有"被放弃"的能力（有界队列 + 丢弃策略），否则积压会拖垮线程与内存

### 踩坑记录
1. **单元测试抓出真实缺陷**：命中路径异常范围过宽（见"关键决策"第 3 条）
2. **E2E 脚本自身的坑（最值得记住）**：PowerShell 5.1 向原生命令传参时会剥离 JSON 双引号，`redis-cli SET` 实际写入的是非法 JSON（日志里出现 `JsonParseException`），导致第一轮"逻辑过期"验证测的其实是"缓存值损坏回源"分支。**教训：E2E 第一轮结果必须用日志/数据交叉验证，否则会得出漂亮但错误的结论**
3. **curl `--parallel` 确实是真并发**（40 请求 92ms vs 串行 1515ms），但 40 个请求的到达间隔（约 2~3ms）大于本机回源耗时（约 3ms）→ 锁窗口几乎不重叠，30/40 并发突发下每个请求都成了 leader，"跟车"一次都没出现
4. **`LOCK TABLES t_link WRITE` 不会阻塞其他会话的普通 SELECT**（InnoDB 快照读/元数据锁的差别），想用表锁人为制造"慢回源"失败
5. Windows 下 Spring Boot 默认日志格式会**缩写超过 40 字符的 logger 名**（`com.shortlink.service.impl.RedirectServiceImpl` → `c.s.service.impl.RedirectServiceImpl`），按包名 grep 日志会漏行，应按类名匹配

| **互斥重建：跟车复用** | 预占重建锁 + 删除缓存 → 前台请求；300ms 后"leader"释放锁并回填 | 前台 302；日志出现「未抢到重建锁」+「跟车成功」；缓存 TTL 保持 leader 写入的 600（若跟车者自行回填会是 1800+抖动）→ **跟车者未回源、未回填** ✓ |
| **互斥重建：等待超时兜底** | 预占重建锁 + 删除缓存 → 请求（窗口内始终无回填） | 302；日志出现 WARN「等待缓存重建超时」；缓存 **EXISTS=0**（兜底不回填，避免写放大）✓ |

- 附带发现（有价值的压测结论）：本机 40 并发突发时"跟车"不发生，因为锁窗口（回源约 3ms）短于请求到达间隔——说明**互斥重建的真实价值场景是"回源变慢"时（慢查询 / 锁等待 / 连接池排队）防止请求堆积**，而不是本机快速回源

## 2026-10-04 · V3.3 多级缓存（Caffeine）+ 防雪崩（限流 / 降级）

### 做了什么
- **L1 本地缓存** `cache/LocalLinkCache`（Caffeine）
  - `maximumSize` + `expireAfterWrite`（默认 30s，远小于 Redis 的 ~1800s）+ 命中率统计
  - 只缓存**正向结果**：不存在/已停用等负向结果不进 L1（防扫描流量灌满本地内存）
- **多实例 L1 失效广播**：`CacheInvalidationPublisher`（Redis Pub/Sub 发布短码）+ `CacheInvalidationListener`（本机失效）+ `config/RedisPubSubConfig`（`RedisMessageListenerContainer`）
  - 语义明确为**尽力而为**：订阅方掉线会丢消息，最终一致性由 L1 短 TTL 兜底
- **降级闸门** `cache/DegradationGuard`：缓存层故障时进入"降级态"（粘滞窗口 10s），对回源 DB 的并发加信号量闸门；拿不到许可的请求抛 `DegradedException` → 全局异常处理转 **503**
  - 许可用 `Permit extends AutoCloseable` 表达：正常态返回空许可、降级态返回真实许可，调用方统一 try-with-resources 释放 → **从 API 层面杜绝许可泄漏**
- **写接口限流** `common/ratelimit/SlidingWindowRateLimiter`（进程内滑动窗口，可注入 `Clock` 便于测试）+ `RateLimitInterceptor`（429 + 统一 Result 结构）+ `config/WebConfig`
  - 只限 POST/PUT/DELETE：跳转链路用降级闸门保护 DB 更贴合场景，且生产环境跳转限流通常前置到 Nginx
- 抽出 `common/util/ClientIpResolver`（原 `RedirectController` 私有方法），跳转与限流共用
- 配置：`shortlink.cache.local.*`（enabled/max-size/ttl-seconds/record-stats）、`shortlink.cache.degradation.*`（max-concurrent-db-queries/acquire-timeout-millis/degrade-window-seconds）、`shortlink.rate-limit.*`
- 测试：新增 `LocalLinkCacheTest`(6)、`DegradationGuardTest`(6)、`SlidingWindowRateLimiterTest`(5，含 8 线程并发恰好放行 100 次的断言)、`RateLimitInterceptorTest`(3)、`CacheInvalidationPublisherTest`(2)、`CacheInvalidationListenerTest`(3)、**`V33BeanWiringTest`(4，Spring 装配冒烟)**，`RedirectServiceImplTest` 增 7 例，`LinkServiceImpl*Test` / `CacheRefreshServiceImplTest` 增两级失效断言

### 关键决策
1. **L1 的正确性问题不回避**：本机改短链必须"清本机 L1 + 删 L2 + 广播"，且广播丢失时靠短 TTL 封顶不一致窗口。刷新路径（逻辑过期重建）也同步更新本实例 L1，避免本地一直返回旧值
2. **限流器不依赖 Redis**：进程内实现。若用 Redis 限流，Redis 故障时"限流器"和"被保护的下游"一起失效 —— 在最需要保护时失去保护；代价是多实例下阈值是"每实例"值（已在类注释写明）
3. **降级不是"拒绝所有请求"**：正常态闸门直接放行（空许可），只有缓存层故障时才限量，且 503 只影响超出并发上限的部分，L1 命中的请求完全不受影响
4. 降级状态采用**粘滞窗口**而非实时探测：避免 Redis 抖动导致正常/降级反复横跳，造成流量脉冲

### 学习点
- 多级缓存（L1 进程内 + L2 共享）的一致性代价：一层是"数据"，一层是"每个实例各有一份"，失效必须广播且必须有 TTL 兜底
- **雪崩的最终形态是依赖整体故障**：此时"降级 + 限流"比"继续硬扛"更重要 —— 宁可少量请求 503，也不能让 DB 挂掉
- 限流的两种实现取舍：进程内（不受下游故障影响、单机阈值）vs Redis（全局阈值、依赖下游）
- 让 Spring 装配问题可见：`ApplicationContextRunner` 冒烟测试（见下"踩坑"）

## 2026-10-04 · V3.4 布隆过滤器性能修复（本地位图）

### 问题（V3.3 的 E2E 顺带发现）
`ShortLinkBloomFilter.mightContain` 对 k=7 个下标逐个 `GETBIT` → **每个跳转请求 7 个 Redis RTT**。
后果有两层：
1. 比它要省掉的那次缓存查询还贵（防穿透的手段比被防的问题更贵）
2. **把 V3.3 的 L1 本地缓存彻底架空**：即使命中本地缓存，仍要 7 次网络往返
实测证据：`CLIENT PAUSE 3000` 时请求被拖到 **3063ms**（Redis 一慢，整条链路跟着慢）

### 修复方案
- 新增 `bloom/BloomBitmapStore`：把"位图的二进制读写"隔离成一层
  - 整块 `GET`/`SET` 位图（**必须走连接层**，用 `StringRedisTemplate` 的字符串 API 整块读二进制会被 UTF-8 解码破坏）
  - 批量 `GETBIT`/`SETBIT` 用 `executePipelined` 合并为 1 个 RTT
- `ShortLinkBloomFilter` 改为**本地位图快照**（`byte[]`，约 1.13MB，字节布局与 Redis 完全一致，无需转换）
  - 启动：位图已存在 → **1 次 GET 整块加载**（实测 `bytes=1186777, bitSize=9585059, hashCount=7`）；不存在 → 从 DB 构建后**1 次 SET 整块写回**（替代过去"每短码 k 次 SETBIT"）
  - 查询：**本地数组判断，零 RTT**；真实流量 99%+ 走这条快路径
  - 创建：本地置位 + pipelined `SETBIT` 写回（1 RTT）
- **解决"本地位图会过期"这个新问题**：只对「本地判定不存在」的结论**回查 Redis 确认**（pipelined，1 个 RTT）
  - Redis 也说不存在 → 安全拦截（只有扫描/不存在的短码才走这条）
  - Redis 说存在 → 本地快照过期（多为其他实例刚创建的短码）→ **放行 + 触发重载**（带 1 秒冷却，防止扫描流量把整块位图反复拉回来）
  - 开关 `shortlink.bloom.verify-on-local-miss`（单实例可关掉省这次 RTT）
- 测试：`ShortLinkBloomFilterTest` 重写为 12 例，覆盖"本地命中零 RTT""回查确认""快照过期自愈""回查关闭""写失败忽略""fail-open"

### 关键决策
1. **不采用"完全信任本地"的极简方案**：那样多实例下会把其他实例刚创建的短码误判为 404 —— 这正是 V3.1 已经踩过一次的 fail-close 事故。多花 1 个 RTT（只在不存在的短码上）换取"绝不误拦"
2. 本地位图直接用 `byte[]` 而不是 `long[]`：字节布局与 Redis 一致，省掉位序转换，杜绝"位序写反"这类隐蔽 bug（并顺手修掉了 V3.1 可能存在的位序隐患面）
3. 重载用"同步 + 冷却 + CAS"而不是再引入线程池：只有快照过期时才发生，1 秒最多一次，实现简单且不会把线程池依赖扩散到 bloom 包

### 验证结果
- 单元测试：**171/171 全绿**（167 → 新增 4 例布隆相关）
- E2E 对照实验（**与缺陷复现完全相同的构造**）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 热短码 + `CLIENT PAUSE 3000` | **3063ms** | **36ms**（不再触碰 Redis）✓ |
| 随机不存在短码 | 404 | 404（回查确认后拦截）✓ |

- 多实例验证（双实例 :8080 / :8081 共用 Redis）：
  - 通过实例#2 创建短码 `1y` → 用**实例#1** 请求 → **302（不是 404）**：本地快照过期被回查机制救回 ✓
  - 日志：`本地快照过期，本次放行并触发重载 ×1` + `本地位图已重载 ×1`，**0 错误**；重载后再次请求直接走本地 ✓

## 2026-10-04 · V3.5 发号器：号段模式（双 buffer）+ 雪花算法

### 做了什么
- **建表** `t_segment`（biz_tag 主键 / max_id / step）：一行一个业务，一次发号 = 一次原子 UPDATE
- **`idgenerator/SegmentAllocator`**：号段分配（`UPDATE max_id = max_id + step` + 同事务 SELECT 读回上界）
  - 独立 Bean + `@Transactional`，因为「同类内部自调用不走 Spring 代理」，而预取发生在后台线程
  - 另有 `raiseTo`（`GREATEST` 只增不减）：跨发号器切换 / 冲突自愈时把起点对齐到 DB 已用最大号之上
- **`idgenerator/SegmentIdGenerator`**（`id-generator-type=segment`）：双 buffer 发号
  - 热路径 `AtomicLong` CAS 自增（无锁）；段切换 `ReentrantLock` + double-check
  - 当前段剩余 ≤ 10%（可配）时**异步预取**下一段；段耗尽直接用预取段（零等待），无预取则同步分配兜底（带重试）
  - 启动时把 `t_segment.max_id` 与**本地 cursor**都对齐到 `MAX(t_link.id)`
  - `recoverAfterConflict()`：抬升 DB 号段 + 本地跳到安全区间
- **`idgenerator/SnowflakeIdGenerator`**（`id-generator-type=snowflake`）：41 位时间戳 + 10 位 workerId + 12 位序列号
  - **时钟回拨**：≤ 上限 → 自旋等待追上；超过 → 抛 `ClockBackwardsException` **拒绝发号**（宁可创建失败也不出重复 ID）
  - 序列号用尽 → 自旋到下一毫秒；`workerId` 配置化（0~1023 校验）；**自定义纪元**默认 2024-01-01（缩短数值 → 短码更短）
  - 时钟抽成字段便于单测构造回拨/进位场景
- **`config/IdGeneratorConfig`**：号段预取线程池（单线程、有界队列、AbortPolicy 让调用方感知拒绝）
- 配置：`shortlink.segment.*`（biz-tag/step/prefetch-remaining-percent/alloc-retry-*）、`shortlink.snowflake.*`（worker-id/epoch-millis/max-backward-millis）
- 测试：`SegmentAllocatorTest`(4)、`SegmentIdGeneratorTest`(8，含 8 线程 × 500 号并发唯一性)、`SnowflakeIdGeneratorTest`(8，含序列号进位与两种回拨)、`IdGeneratorBenchmarkTest`（按需开启的横向基准）
- 压测报告：`docs/benchmark/V3.5-发号器对比.md`（真实 Redis/MySQL 实测数据）

### 实测数据（单线程每号耗时，详见压测报告）

| 方案 | 每号耗时 |
|---|---|
| `segment`（内存发号） | **0.29 µs** |
| `snowflake`（本地生成） | **0.34 µs** |
| `segment`（含真实 DB 分配，step=1000 摊销） | **7.16 µs** |
| `redis-incr`（每号一次 RTT） | **158.15 µs** |
| `db-auto-increment`（每号一次 INSERT） | **1393.33 µs** |

结论：**发号方案的性能差异本质是"要不要走网络/存储"**，相差 2~3 个数量级；号段把 DB 调用降到 1/step（step=1000 时约 22 倍于 Redis INCR）。

### 关键决策
1. **短链短码优先号段，而不是雪花**：雪花 ID 的 Base62 短码实测 **10 位**，号段只有 **2 位**（同一批 E2E 对照）。雪花更适合订单号这类"不需要短"的场景
2. 号段起点必须**同时**对齐 DB 与本地 cursor：只对齐 DB 会让首段从 1 开始，直接覆盖已用过的号（已用单测锁定该行为）
3. 预取失败/未就绪时**同步分配兜底**，而不是让创建失败；段被浪费是号段模式的正常代价
4. 时钟回拨"大幅直接拒绝"而不是"退化成等待"：重复 ID 会以"偶发创建失败"的形式出现，比明确报错难排查得多

### 踩坑记录（本轮抓到一个真实生产级缺陷）
1. **MySQL 排序规则坑（重要）**：`t_link.code` 用默认的 `utf8mb4_general_ci`（**大小写不敏感**），而 Base62 字符集同时含 `a-z` 与 `A-Z`，于是 `"2A"` 被判为与已存在的 `"2a"` **重复**：
   - 现象：30 并发创建出现 23~26 次 `Duplicate entry 'localhost:8080-2A' for key 't_link.uk_domain_code'`，id 空间出现大量空洞（98~123、154~181 等号被白白浪费）
   - 更隐蔽的影响：`WHERE code = '2A'` 会命中 `2a` 的记录 → **/2A 与 /2a 指向同一条记录**，短码语义被破坏
   - 为什么以前没被发现：创建链路有「冲突 → 自愈 → 重试」兜底，把它掩盖成"偶发冲突"，直到高并发 E2E 才暴露
   - 修复：`ALTER TABLE t_link MODIFY code VARCHAR(16) COLLATE utf8mb4_bin`（并在 schema.sql 写明原因）。实测冲突 **23 → 0**，且 `3c`(id 198) 与 `3C`(id 224) 可共存
   - 教训：**字符集/排序规则是数据模型的隐藏约束**，Base62 这类混合大小写的编码必须显式声明区分大小写
2. **初始 cursor 未对齐 DB 最大号**：首段会覆盖已用过的号（单测 `seedAlignsLocalCursorToDbMaxId` 覆盖）
3. Mockito 给 varargs 方法（`JdbcTemplate.update`）打桩要用 `any(Object[].class)` 匹配整组，否则参数个数不同会触发 `PotentialStubbingProblem`

## 2026-10-04 · V3.5 审查修复（3 中危 + 2 低危）

### 修复清单

| # | 问题 | 严重程度 | 修法 |
|---|---|---|---|
| 1 | 缓存刷新线程池用 `DiscardPolicy`：静默丢弃、不抛异常 → 调用方 `catch (RejectedExecutionException)` 成**死代码**，「在飞标记」`refreshingCodes` 泄漏 → 该短码在本实例**永久无法再触发刷新** | 🟠 中 | `CacheExecutorConfig` 改 `AbortPolicy`（与 `IdGeneratorConfig` 一致），并**在装配测试中断言策略**，把选择钉死 |
| 2 | 雪花 `epoch-millis` 未校验：纪元晚于当前时间 → `now-epoch` 为负 → ID 为负 → `Base62Codec` 抛异常，表现为"创建接口偶发 500"，与真实原因相距甚远 | 🟠 中 | 构造器启动即校验，非法直接启动失败；补单测 |
| 3 | `t_link_stats.code` 仍是大小写不敏感（与已修的 `t_link.code` 同类问题，统计按短码查询会串） | 🟠 中 | schema + `ALTER TABLE` 同步 `COLLATE utf8mb4_bin` |
| 4 | `SegmentAllocator.ensureRow` 用 `UPDATE ... SET max_id = max_id` 探测行是否存在：MySQL 的 affected-rows 是**实际改变的行数**，行存在也返回 0 → 每次分配都白跑一条 `INSERT IGNORE`（多一次写 + 多拿一次行锁） | 🟡 低 | 改 `SELECT COUNT(1)` 只读探测；补回归测试 `allocateSkipsInsertWhenRowExists` |
| 5 | 装配冒烟测试未覆盖 V3.5 新 Bean（上次"两构造器导致启动失败"正是这类问题） | 🟡 低 | 合并为 `config/BeanWiringTest`（8 用例）：两个发号器 + 布隆位图存储 + 线程池策略 + V3.3 四个组件 |

**关于 #1 的教训（值得单独记）**：单测当时"通过"了，是因为测试注入了**自己写的会抛异常的 executor**，
而生产注入的是 `DiscardPolicy` —— **测试桩与生产实现不一致，测试就变成了自我安慰**。
修法是「让生产策略与分析路径一致」+「把策略写成断言」，而不是改测试。

### 验证结果
- 单元测试：**198/198 全绿**（192 → 新增 6 例；含 1 个默认跳过的基准）
- 冒烟（号段模式实跑）：启动 → 创建短链 → 跳转 **302** ✓（确认新的 COUNT 探测 SQL 在真实 MySQL 上工作）
- 库结构核对：`information_schema` 显示 `t_link.code` 与 `t_link_stats.code` **均为 utf8mb4_bin** ✓

### 冒烟时顺带印证的运营结论
同库混用发号器会让 **id 空间前跳**：此前雪花 E2E 产生的 `3.65e17` 级 id 抬高了 `MAX(t_link.id)`，
切回号段后种子直接对齐到该值 → 后续 id 都是 `3.65e17` 量级 → **短码从 2 位变 10 位**。
这属预期行为（号只要求唯一、不要求连续），但真实系统必须做到
「**同一 id 空间、同一时刻只启用一种发号器**」，且切换后要接受短码变长。

### 未修复（记录 / 待决策，非常规缺陷）
- **布隆过滤器整块 `SET` 预热 vs 并发新增**的覆盖窗口（fail-close 方向、概率极低）：
  修法需要"批量 SETBIT 合并"或预热期分布式锁，属**性能 vs 安全**权衡，需先决定取舍
- **可观测性出口**：L1 命中率 / 降级拒绝数 / 限流拒绝数已实现但无接口暴露（建议加只读诊断接口）
- **无 `@SpringBootTest` 集成测试**：跳转 L1+L2+DB 全链路仅靠 E2E 覆盖，回归成本高
