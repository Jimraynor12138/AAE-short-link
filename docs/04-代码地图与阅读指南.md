# 代码地图与阅读指南

> 本文件回答一个问题：**按当前配置，项目里哪些类真正生效？按什么顺序读最省时间？**
>
> 项目按 V0→V3.5 演进，代码里保留了「配置开关」与「接口多实现」——这是压测对照实验的基础，
> 不是废弃代码。直接打开 `src/main/java` 容易被绕晕，所以：**先看配置，再看代码。**

---

## 1. 先看配置：默认值决定了「哪条路真正生效」

配置文件：`src/main/resources/application.yml`，连接信息见 `application-dev.yml`。

| 开关 | 默认值 | 关闭后的行为 |
|---|---|---|
| `shortlink.cache.enabled` | `true` | 跳转直查 DB（等价 V0，也是压测基线） |
| `shortlink.cache.local.enabled` | `true` | 不启用 L1 本地缓存 |
| `shortlink.bloom.enabled` | `true` | 不做布隆过滤器前置拦截 |
| `shortlink.cache.anti-breakdown.logical-expire-enabled` | `true` | 不做「逻辑过期 + 异步重建」 |
| `shortlink.cache.anti-breakdown.mutex-rebuild-enabled` | `true` | 缓存未命中时不加互斥锁（并发全部回源） |
| `shortlink.cache.degradation.enabled` | `true` | 不做降级闸门保护 |
| `shortlink.stats-enabled` | `true` | 不记录访问统计 |
| `shortlink.mq.enabled` | `true` | 统计退化为同步直写（V1 行为） |
| `shortlink.id-generator-type` | **`auto`** | 见下一节 |

> `docs/benchmark/` 中的 S1~S5 五个压测场景，就是靠启动参数切换这些开关实现的。

## 2. 接口多实现：同一时刻只有一个被装配

实现类上的 `@ConditionalOnProperty` 决定谁进 Spring 容器：

| 接口 | 实现类 | 生效条件 | 默认是否生效 |
|---|---|---|---|
| `IdGenerator` | `AutoIncrementIdGenerator` | `id-generator-type=auto`（缺省即此） | ✅ |
| | `RedisIncrIdGenerator` | `id-generator-type=redis` | ❌ |
| | `SegmentIdGenerator` | `id-generator-type=segment` | ❌ |
| | `SnowflakeIdGenerator` | `id-generator-type=snowflake` | ❌ |
| `VisitRecorder` | `AsyncVisitRecorder` | `mq.enabled=true` | ✅ |
| | `SyncVisitRecorder` | `mq.enabled=false` | ❌ |
| MQ 组件 | `RabbitMqConfig` / `VisitMessageProducer` / `VisitStatsConsumer` | `mq.enabled=true` | ✅ |

**结论：默认配置下只有「DB 自增发号器」和「MQ 异步访问记录」在生效**，其余实现是配置切换项。

## 3. 四条生效链路

### 3.1 跳转（核心读链路）

```
GET /{code}
└─ RedirectController.redirect                         → 302 + Location；不存在/停用/过期/脏 URL → 404
   └─ RedirectServiceImpl.resolveRedirectUrl
      ├─ ① ShortLinkBloomFilter.mightContain(code)      判定「一定不存在」→ 直接返回 null（404）
      │     └─ BloomBitmapStore                         本地内存位图（零 RTT）
      │           └─ 本地判「不存在」时回查一次 Redis 确认（多实例本地快照可能过期）
      ├─ ② LocalLinkCache.get(key)                      L1 命中 → 校验 + 可能触发异步重建 → 返回
      ├─ ③ Redis GET（StringRedisTemplate）              L2 命中 → 回填 L1 → 校验 → 返回
      │     ├─ DegradationGuard.markHealthy()           读成功 → 退出降级态
      │     └─ DegradationGuard.markDegraded(...)       读异常 → 进入降级态
      ├─ ④ CacheRebuildLock.tryLock(code)               抢到=leader；未抢到=follower 轮询等待
      ├─ ⑤ DegradationGuard.tryAcquirePermit()          回源许可（降级态限量；拿不到 → 503）
      ├─ ⑥ LinkMapper.selectOne(QueryWrapper)           MySQL 兜底
      ├─ ⑦ 回填 L2（TTL 抖动）+ 回填 L1
      └─ ⑧ VisitRecorder.record(...) → AsyncVisitRecorder 只投递消息即返回
             └─ VisitMessageProducer.send(...)
```

### 3.2 创建（写链路）

```
POST /api/v1/link/create
└─ LinkController → LinkServiceImpl.createLink
   ├─ IdGenerator.nextId()                   默认走 AutoIncrementIdGenerator
   ├─ Base62Codec.encode(id)                 得到短码
   ├─ LinkMapper.insert(...)                 (domain, code) 唯一索引兜底
   │     └─ DuplicateKeyException → idGenerator.recoverAfterConflict() → 重试（≤3 次）
   └─ ShortLinkBloomFilter.add(code)         **插入成功之后**才写布隆过滤器
```

### 3.3 修改 / 删除（缓存一致性，Cache Aside）

```
LinkServiceImpl.updateLink / deleteLink
├─ 先改库（updateById / deleteById 逻辑删除）
└─ evictLinkCache(code)
   ├─ LocalLinkCache.invalidate(key)          本机 L1
   ├─ Redis DELETE(key)                       L2
   └─ CacheInvalidationPublisher.publish     广播 → CacheInvalidationListener 清其他实例 L1
```

### 3.4 统计（MQ 异步 + 定时落库）

```
VisitMessageProducer → RabbitMQ(exchange → queue) → VisitStatsConsumer
├─ IdempotentChecker.check(...)       幂等：Redis 去重键（TTL 60s）
├─ StatsServiceImpl.recordVisit(...)  PV / UV（HyperLogLog 去重）/ IP / 来源 / 设备
├─ StatsSnapshotService.markDirty     标记脏数据
└─ @Scheduled 每 2s 批量 upsert → t_link_stats（另有 10 分钟兜底扫描，自愈重启丢标记）
   └─ 消费失败重试 3 次 → 死信队列 short-link.visit.dlq
```

## 5. 两个容易混淆的机制：物理过期 vs 逻辑过期

| | L1（Caffeine） | L2（Redis） | 缓存值里的 `logicalExpireAt` |
|---|---|---|---|
| 过期形式 | **物理过期**：`expireAfterWrite`，默认 30s | **物理 TTL**：1800s + 随机抖动 [0,600] | **逻辑过期**：默认 300s |
| 到期后果 | 条目从内存消失 → 读到 null | key 消失 → 回源 DB | 值仍在、仍可返回旧值 → 触发后台异步重建 |
| 设计原因 | L1 是多实例各一份，广播可能丢 → 用短 TTL 把不一致窗口封顶 | 缓存失效不集中 → 防雪崩 | 跳转场景 URL 基本不变，短暂陈旧可接受 → 换请求线程零阻塞 |

**关键点：两者是正交的。** L1 能不能读到值由**物理过期**决定；读到值之后要不要触发重建由缓存值里的**逻辑过期字段**决定。
`RedirectServiceImpl` 中 L1 命中分支同样调用 `isLogicallyExpired(...)`，原因就在这里——L1 的值是从 L2 回填的，携带同一个逻辑过期时间。

## 7. 常见误解（读代码/面试时最容易说错的地方）

| # | 错误说法 | 正确说法 |
|---|---|---|
| 1 | 布隆过滤器用来判断短码是否**撞号** | 撞号由 **MySQL `(domain, code)` 唯一索引**判定；布隆过滤器只能回答「一定不存在 / 可能存在」，且**不支持删除**，无法用于去重校验 |
| 2 | 创建时**先写布隆过滤器**再判断冲突 | 顺序相反：**插入 DB 成功之后**才 `bloomFilter.add`，否则新短码会被自己的防穿透误拦 |
| 3 | MQ 统计发生在**发号 / 创建**时 | 统计发生在**跳转（访问）时** |
| 4 | 布隆判定「不存在」后去查本地缓存 | 判定「一定不存在」→ **直接 404**；放行后才查 L1 |
| 5 | L1 也有逻辑过期 | L1 的「读不到」由**物理过期（30s）**决定；`logicalExpireAt` 只决定「是否触发异步重建」 |
| 6 | Redis 挂掉后所有请求都去查 DB | 降级态下回源并发被**闸门限制**（默认每实例 20），超出部分快速返回 **503** |
| 7 | L1 命中也要访问 Redis | **不访问**。所以 Redis 整体故障时，热门短码仍能正常跳转（实测：杀掉全部 Redis 连接后仍 302 / 48ms） |
| 8 | 布隆过滤器判定「不存在」就直接信 | 本地位图可能过期，**判「不存在」时要回查一次 Redis 确认**，否则会把其他实例刚创建的短码误拦成 404 |

## 8. 30 分钟读码路线（三遍法）

**准备（2 分钟）**：先看本文第 1、2 节，明确默认配置下哪些类生效。

| 遍数 | 做什么 | 时间 |
|---|---|---|
| 第 1 遍 | 只读 `RedirectServiceImpl.resolveRedirectUrl` 的编号注释（`// 0.` ~ `// 6.`）与 if 分支，**不点进任何 private 方法** | 10 分钟 |
| 第 2 遍 | 挑一个概念钻进去：例如「逻辑过期」→ 读 `isLogicallyExpired` → `triggerRefresh` → `CacheRefreshServiceImpl.refreshAsync` | 10 分钟 |
| 第 3 遍 | 用问题反查代码：例如「Redis 挂了会怎样？」→ 读第 2 步的 `try/catch` → `markDegraded` → `findByCodeWithPermit` | 10 分钟 |

**进阶（各 30 分钟）**：
1. `bloom/ShortLinkBloomFilter` + `BloomBitmapStore`：本地位图、缺失回查、fail-open
2. `idgenerator/SegmentIdGenerator` + `SegmentAllocator`：双 buffer 预取与号段切换
3. `mq/consumer/VisitStatsConsumer` + `IdempotentChecker`：幂等与死信
4. `cache/DegradationGuard`：粘滞窗口、许可（`Permit` 用 `AutoCloseable` 表达，避免泄漏）

**动手验证**（比读 10 遍有用）：

```bash
# 关闭逻辑过期，观察行为差异
java -jar target/short-link-0.1.0-SNAPSHOT.jar --shortlink.cache.anti-breakdown.logical-expire-enabled=false

# 制造 Redis 卡顿，观察本地缓存与本地位图如何兜住（对照开发日志 V3.4）
redis-cli CLIENT PAUSE 3000

# 收紧降级闸门后并发请求，复现 503
java -jar target/short-link-0.1.0-SNAPSHOT.jar \
  --shortlink.cache.degradation.max-concurrent-db-queries=1 \
  --shortlink.cache.degradation.acquire-timeout-millis=1
```
