# V1 压测报告：跳转链路（缓存 / 统计 的收益与代价）

> 时间：2026-10-02 · 环境：Windows 11 / JDK 17 / MySQL 8 / Redis 7（本机）· 工具：Apache JMeter 5.6.3

## 1. 压测目标

用数据回答两个问题：

1. **V1.1 的 Redis 缓存到底带来多少收益？**（对比 V0 等价的直查 DB 路径）
2. **V1.3 的同步统计（3 次 Redis 写）代价有多大？**（判断 V2 引入 MQ 异步化是否有必要）

## 2. 测试方法

**同一份代码 + 配置开关**，避免版本切换带来的环境差异：`shortlink.cache.enabled` 与 `shortlink.stats-enabled` 组合出 2×2 四种场景。

| 场景 | 缓存 | 统计 | 含义 |
|---|---|---|---|
| S1 | ✗ | ✗ | **V0 等价基线**（每次跳转直查 DB，无统计） |
| S2 | ✓ | ✗ | 只有缓存的收益 |
| S3 | ✓ | ✓ | **V1 现状** |
| S4 | ✗ | ✓ | 只有统计的代价 |

**压测参数**（四个场景完全一致）：

- 目标：`GET /3`（热点短码，单 key）
- 预热：20 线程 × 100 次 = 2000 请求（**关键**：不做预热会把 JIT 编译开销算进结果，实测能差出 5 倍）
- 采集：100 线程 × 200 次 = **20000 请求**，ramp-up 1s，keep-alive 开启，不跟随重定向
- 每个场景前：清空该短码的缓存 key，重启应用（开关是启动期配置）
- 断言：HTTP 302

**复现命令**：

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File docs\benchmark\run-benchmark.ps1 -Only "S1" -Threads 100 -Loops 200 -Ramp 1 -WarmThreads 20 -WarmLoops 100
```

## 3. 结果

| 场景 | 缓存 | 统计 | QPS | avg | p50 | p95 | p99 | max | 错误率 |
|---|---|---|---|---|---|---|---|---|---|
| **S1** V0 等价基线 | ✗ | ✗ | 3442.9 | 25.01ms | 14ms | 86ms | 187ms | 637ms | 0% |
| **S2** 仅缓存 | ✓ | ✗ | **5369.1** | **15.70ms** | 15ms | **30ms** | **47ms** | **121ms** | 0% |
| **S3** V1 现状 | ✓ | ✓ | 3438.8 | 26.57ms | 25ms | 47ms | 60ms | 74ms | 0% |
| **S4** 仅统计 | ✗ | ✓ | 2488.5 | 37.54ms | 35ms | 58ms | 97ms | 354ms | 0% |

## 4. 结论

### 4.1 缓存收益显著（S1 → S2）

| 指标 | S1 | S2 | 变化 |
|---|---|---|---|
| QPS | 3443 | 5369 | **+56%** |
| avg | 25.0ms | 15.7ms | -37% |
| p95 | 86ms | 30ms | **-65%** |
| p99 | 187ms | 47ms | **-75%** |
| max | 637ms | 121ms | -81% |

**长尾改善远大于均值改善**——这正是缓存的价值所在：命中缓存的请求不再占用 DB 连接，消除了连接池排队（Hikari 池只有 10 个连接，而并发线程有 100 个），所以 p99/max 的抖动被大幅削平。

### 4.2 同步统计代价巨大（S2 → S3、S1 → S4）

| 对比 | QPS 变化 | avg 变化 |
|---|---|---|
| S2 → S3（加统计） | 5369 → 3439（**-36%**） | 15.7 → 26.6ms（**+69%**） |
| S1 → S4（加统计） | 3443 → 2489（**-28%**） | 25.0 → 37.5ms（**+50%**） |

**V1 现状（S3）的吞吐几乎回落到 V0 基线（S1）水平：缓存赚到的性能，被同步统计（PV 的 INCR + UV/IP 两次 PFADD，共 3 次 Redis 往返）几乎抵消。**

这就是 **V2 引入 RabbitMQ 的直接依据**：把统计从跳转 RT 中剥离。V2 的验收标准可以量化为：**S3 的 QPS 应回到接近 S2（≈5000+）的水平**。

### 4.3 另一个意外观察

S3 的 p99（60ms）其实优于 S1（187ms）——因为统计带来的开销是**均匀**的（每个请求固定 +3 次 Redis 往返），而 DB 路径的排队是**有偏**的（连接池耗尽时部分请求长尾极严重）。这解释了为什么 S4 的 max（354ms）反而比 S1（637ms）低。

## 5. 局限性（重要，避免过度解读）

1. **压测客户端与服务端同机**：JMeter、应用、MySQL、Redis 共享一台 16 核机器，JMeter 自身也要吃 CPU。因此**绝对 QPS 不代表服务端容量**，只能用于同环境下的横向对比。
2. **单轮采集**：每个场景只跑 1 次，未做多轮取中位数/方差分析。后续版本建议每场景 3 轮。
3. **数据量过小**：`t_link` 仅 22 行且全在 InnoDB buffer pool 中，DB 点查成本被严重低估；生产环境数据量下 S1/S4 会更差。
4. **单热点短码**：只压了一个 code，未考察缓存命中率随短码集合变化的影响（长尾短码会走回源路径）。
5. **连接池未调优**：Hikari 固定 10 连接（V0 遗留配置），100 并发下它才是真正的瓶颈；生产需按并发量核算。

## 6. 过程记录：本次踩到的两个压测坑

1. **JMeter 默认向已存在的 JTL 追加样本**：第二次跑 S1 时，文件里混入了上一次的 10000 条样本，时间跨度被算成 1873 秒，QPS 直接算成 10.7（严重失真）。解决：`jmeter -f`（强制覆盖）+ 运行前删除旧文件。
2. **预热不足会让数据完全失真**：同一个 S1 场景，预热 200 请求时 avg=16.38ms / p95=56ms；预热 2000 请求后 avg=3.19ms / p95=6ms（低并发下）。JIT 编译与连接池初始化都被算进了"服务端延迟"。
