# V2 压测报告：统计异步化（RabbitMQ）

> 时间：2026-10-02 · 环境：Windows 11 / JDK 17 / MySQL 8 / Redis 7 / RabbitMQ 3.13.7（全部本机）· 工具：JMeter 5.6.3

## 1. 目标与验收标准

V1 压测发现的问题：**同步统计让跳转吞吐下降 28%~36%**（3 次 Redis 往返 + UA/Referer 解析都在请求线程里）。

V2 的改造：跳转链路只投递一条 MQ 消息就返回，解析与统计写入全部搬到消费端。

**事先定下的验收标准**：S3 场景（缓存+统计）QPS 从 3439 回到 **5000+**，avg 回到 **15ms 量级**。

## 2. 场景定义

| 场景 | 缓存 | 统计 | 统计实现 | 含义 |
|---|---|---|---|---|
| S3 | ✓ | ✓ | 同步（V1 行为） | 对照组 |
| S5 | ✓ | ✓ | **MQ 异步（V2）** | 本次改造目标 |

参数：100 或 200 线程，每次 20000 请求，ramp 1s，预热 2000 请求（20×100），每场景前清空短码缓存 key 并重启应用。

## 3. 结果

### 3.1 100 线程（客户端未饱和）

| 场景 | QPS | avg | p50 | p95 | p99 | max | 错误率 |
|---|---|---|---|---|---|---|---|
| S3 V1 同步统计 | 2872.7 | 32.34ms | 34ms | 50ms | 66ms | 80ms | 0% |
| **S5 V2 MQ 异步** | **3672.4** | **24.33ms** | 26ms | 54ms | 75ms | 175ms | 0% |
| 变化 | **+28%** | **-25%** | -24% | +8% | +14% | — | — |

### 3.2 200 线程（服务端/环境饱和）

| 场景 | QPS | avg | p50 | p95 | p99 | max | 错误率 |
|---|---|---|---|---|---|---|---|
| S3 V1 同步统计 | 2752.9 | 68.91ms | 69ms | 108ms | 132ms | 153ms | 0% |
| S5 V2 MQ 异步 | 3076.4 | 58.51ms | 49ms | 165ms | 250ms | 389ms | 0% |

| 变化 | +12% | **-15%** | -29% | — | — | — | — |

## 4. 结论

### 4.1 改造方向正确，但**未达成 5000+ 的验收目标**

- 100 线程下 QPS +28%、平均延迟 -25%，方向与预期一致；
- 但绝对吞吐没能回到 S2（仅缓存，5369 QPS）的水平，**验收标准的 5000+ 未达标**。

### 4.2 未达标的真实原因：测量环境饱和，不是架构问题

关键证据：**S3 从 100 线程加到 200 线程，吞吐不增（2873 → 2753）而延迟翻倍（32ms → 69ms）** —— 这是典型的服务端/环境饱和特征。同理 S5 也只从 3672 降到 2933。

瓶颈来源（本机 16 核，所有组件同机）：

1. JMeter 自身 200 线程 + Broker + 消费端（每消息 5 次 Redis 写）+ 定时落库 + 应用，全部争抢同一批 CPU；
2. RabbitMQ 单机部署，publish 也要占 CPU/网络栈；
3. 消费端在压测期间实际处理了 2 万条消息（5 次 Redis 写/条 = 10 万次 Redis 操作），这部分 CPU 开销被算在了"跳转压测"的窗口里。

即便如此，**跳转路径本身的收益是确定的**：同一线程数下延迟稳定下降 15%~25%（因为请求线程里只剩「1 次 publish」而不是「5 次 Redis 写 + 解析」）。

### 4.3 MQ 的核心价值在本次压测中得到了直接验证：削峰填谷

压测结束后队列状态（真实数据）：

```
messages = 16483   consumers = 0（应用已停止）
```

- 生产端（跳转）约 3000-3700 msg/s，**单消费者处理不过来**，积压 1.6 万条消息；
- 但**跳转完全没有被拖慢** —— 消息在 Broker 里排队，这就是异步化的意义；
- 消费端可以通过「提高并发（已配 concurrency=2 / max-concurrency=8）或增加实例」水平扩容来追平，与跳转服务解耦扩缩容；
- 实测把消费端并发从 1 调到 2，对跳转 QPS 无影响（符合预期：跳转不等消费端）。

## 5. 功能正确性验证（比吞吐更重要）

| 验证项 | 方式 | 结果 |
|---|---|---|
| 消息投递 | RabbitMQ 管理台 | publish=8（4+4 次请求），redeliver=0 |
| 拓扑声明 | 管理 API | 主队列 durable 且带 DLX 参数，死信队列已建，消费者已连接 |
| 统计维度 | `GET /api/v1/stats/3` | `pv/uv/ipCnt` + `refererStats{direct,www.baidu.com}` + `deviceStats{pc,mobile}` 全部正确 |
| 快照落库 | `SELECT * FROM t_link_stats` | 2 秒内写入，`link_id=3, pv, uv, ip_cnt, default_cnt=2, referer/device JSON` 与 Redis 口径一致 |
| 消费幂等 | 单元测试 + 观察 | 重复消息被跳过（PV 不被多加） |
| 死信队列 | 向交换机投递非法 JSON | 重试 3 次后进入 `short-link.visit.dlq`（messages=1），不再无限重投 |
| 降级路径 | `--shortlink.mq.enabled=false` | 自动切换为同步统计（V1 行为），跳转不受 MQ 可用性影响 |

## 6. 下一步建议（让验收标准具备可测条件）

1. **压测客户端与 Broker 分离**：JMeter 跑在另一台机器/容器，消除客户端 CPU 争抢（这是本次最大的测量缺陷）；
2. **消费端独立部署**：消费者单独起实例，观察「跳转 QPS 与消费 TPS」两条独立曲线；
3. **补充长时间稳定性测试**：连续压测 10 分钟，观察队列积压是否最终收敛（即消费者吞吐 ≥ 生产速率）；
4. V3 再做时，可直接复用本脚本的场景 S5 作为新的基线。

## 7. 诚实说明

- 单轮采集，无多轮方差分析；200 线程的两组数据差异（3076 vs 2933）已在噪声范围内。
- 本机同机部署环境下，**绝对 QPS 不代表服务端容量**，只用于同环境的横向对比。
- 未做「消息持久化 + Broker 重启」的不丢消息验证（当前为 fire-and-forget 语义，允许偶发丢失，这是与用户确认过的取舍）。
