# V3.5 发号器横向对比（号段 / 雪花 / Redis / DB 自增）

> 生成方式：`IdGeneratorBenchmarkTest`（默认跳过，需显式开启）
> ```bash
> mvn -B test -Dtest=IdGeneratorBenchmarkTest -Dshortlink.benchmark=true
> ```
> 测试环境：Windows 本机，JDK 17.0.13，MySQL 8（localhost），Redis（localhost:6379）
> 测量口径：**单线程串行取号**，预热 10% 后计时；每个用例都断言 ID 唯一性（性能再好也不能重号）
>
> ⚠️ **副作用提示**：该基准会真实改动开发环境的发号状态 ——
> `t_segment.max_id` 前进约 20 万、Redis 发号 key（`short-link:id-generator`）前进 5 万、
> `t_sequence` 新增约 2200 行。号只要求唯一，因此不影响后续使用（id 会整体前移），
> 但**不要在需要保持 id 连续的场合跑**，也不要在意"短码变长了"。

## 测量结果

| 方案 | 取号总量 | 总耗时 (ms) | 每号耗时 (µs) | 相对最慢的倍数 |
|---|---:|---:|---:|---:|
| `segment`（内存发号路径） | 1,000,000 | 292.6 | **0.29** | — |
| `snowflake`（本地生成） | 1,000,000 | 338.2 | **0.34** | — |
| `segment`（含真实 DB 分配，step=1000 摊销） | 200,000 | 1,432.4 | **7.16** | — |
| `redis-incr`（每号一次 RTT） | 50,000 | 7,907.5 | **158.15** | 22× |
| `db-auto-increment`（每号一次 INSERT） | 2,000 | 2,786.7 | **1,393.33** | 195× |

## 怎么看这组数据（避免误读）

1. **前三行才是"发号"本身的成本**
   - `segment` 内存路径 0.29µs、`snowflake` 0.34µs：都是纯本地操作（原子自增 / 位运算），数量级相同
   - `redis-incr` 158µs ≈ **一次本机 Redis 往返**；`db-auto-increment` 1393µs ≈ **一次本机 MySQL INSERT**
   - 也就是说：**发号方案的性能差异，本质是"要不要走网络/存储"，差 2~3 个数量级**

2. **号段模式的 7.16µs 是摊销值，且与 step 成反比**
   - 实测一次号段分配 ≈ **7ms**（本机 MySQL，UPDATE + SELECT 两步，含事务提交）
   - `step=1000` → 每号摊销 7µs；`step=10000` → 约 0.7µs；`step=100` → 约 70µs
   - 调节旋钮很直观：**step 越大 → 发号成本越低，但重启浪费的号越多**

3. **snowflake 的 0.34µs 不代表"CPU 只花 0.34µs"**
   - 12 位序列号上限是 **4096 个/毫秒**，所以 100 万个号至少要跨 244 毫秒
   - 实测 338ms ≈ "被毫秒进位限制"而非 CPU 瓶颈：**单机上限约 409.6 万/秒**（4096 × 1000ms）
   - 短链创建的真实 QPS 远低于此，所以它是"能力过剩但代价是短码变长"

4. **本机数据偏乐观**
   - 本机 loopback 的 Redis/MySQL RTT 比真实机房网络小；换成同机房 ~0.5ms、跨机房 ~2ms，`redis-incr` 与"每号一次 DB"会更难看
   - 单线程测量不含锁竞争与连接池排队；真实 QPS 还要受并发与连接池上限约束

## 结论（本项目为什么这么选）

| 场景 | 推荐 | 理由 |
|---|---|---|
| **短链短码** | 号段模式（或预生成号池） | 号小 → 短码短（本项目实测 1~3 位 vs 雪花约 10 位）；成本低且可调 |
| 订单号 / 消息 ID | snowflake | 不要求"短"，但要求本地生成、高吞吐、趋势递增 |
| 小流量内部系统 | DB 自增 | 实现最简，成本可接受 |
| 已有 Redis 且追求简单 | Redis INCR | 一号一次 RTT，量小时够用；量大时升级号段 |

> 一句话：**没有最好的发号器，只有匹配业务形态的发号器。** 短链要"短"，所以时间戳类方案（雪花）反而不是首选 —— 这正是本项目把四种都实现一遍的价值。

## 附：正确性验证（同一批测试断言）

- 1,000,000 个雪花 ID、1,000,000 个号段 ID、200,000 个真实 DB 号段 ID → **无重复**
- 号段模式并发测试（8 线程 × 500 号）→ **无重复**（`SegmentIdGeneratorTest`）
- 雪花时钟回拨：小幅（≤5ms）自旋等待后仍递增；大幅回拨**拒绝发号**（`ClockBackwardsException`）
